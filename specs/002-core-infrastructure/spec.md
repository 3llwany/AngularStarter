# مواصفة الميزة: المرحلة الثانية — البنية التحتية الأساسية لتطبيق مذاكرتي

**فرع الميزة**: `002-core-infrastructure`
**تاريخ الإنشاء**: 2026-11-15
**الحالة**: معتمد ومنفّذ

**المدخل**: المرحلة الثانية (`Core`) لمشروع مذاكرتي: تأسيس نظام المصادقة، التحكم بالصلاحيات، البنية التحتية لـ HTTP، خدمة تحسين محركات البحث (SEO)، سجل التنقل الديناميكي، وإدارة الأخطاء؛ دون بناء شاشات أعمال أو قوالب العرض النهائية (والتي تبدأ في المرحلة الثالثة)، مع محاكاة الـ API خلف طبقات تجريد لحين اعتماد عقد الباك إند النهائي.

## سيناريوهات المستخدمين والاختبارات *(إلزامي)*

### قصة المستخدم 1 — تسجيل الدخول حسب الدور ودورة حياة الجلسة (الأولوية: P1)

يستطيع أي مستخدم ينتمي لأحد الأدوار الخمسة الأساسية (طالب بالبريد الإلكتروني، ولي أمر برقم الموبايل، معلم بكود المعلم، مدرسة بكود المدرسة، شريك متجر ببريد العمل) تسجيل الدخول بالمعرّف المناسب لدوره وكلمة المرور عبر استراتيجيات محاكية خلف تجريد `AuthApi`، ومشاهدة حالة الجلسة التفاعلية (`user`, `role`, `status`) والاحتفاظ بالجلسة عند إعادة تحميل المتصفح عبر الاستعادة من الخادم دون حفظ أي توكنات في `localStorage` أو `sessionStorage`، وتسجيل الخروج بنظافة.

**لماذا الأولوية P1**: جميع مسارات الأدوار وميزات المراحل القادمة تعتمد على مصدر موحد وموثوق لهوية المستخدم وحالة جلسته.

**الاختبار المستقل**: تنفيذ الدخول للأدوار الخمسة، التأكد من تحديث إشارات الجلسة والبقاء بعد إعادة التحميل دون لمس Web Storage، وتصفير الحالة عند الخروج.

**سيناريوهات القبول**:

1. **معطى** زائر يقدّم بيانات صحيحة تناسب معرّف دوره، **عند** نجاح الدخول، **تُحدّث** إشارات `user` و `role` و `status` (`authenticated`) وتتزامن السمة اللونية للدور.
2. **معطى** مستخدم مصادق عليه يعيد تحميل الصفحة في المتصفح، **عند** التهيئة على مسار محمي أو عند وجود تلميح الجلسة، **تُستعاد** الجلسة من الخادم دون أي قراءة أو كتابة في `localStorage`/`sessionStorage`.
3. **معطى** مستخدم مسجل، **عند** إتمام `logout()`، **تُمسح** بيانات `user` وتعود `status` إلى `anonymous`.
4. **معطى** بيانات دخول خاطئة أو مرفوضة، **عند** فشل المحاولة، **تبقى** الحالة `anonymous` ولا يُحتفظ بأي بيانات جزئية.

---

### قصة المستخدم 2 — حماية المسارات وعزل شيفرة الأدوار (الأولوية: P1)

لا يمكن للمستخدم المسجل فتح إلا مسارات دوره فقط؛ محاولة فتح مساحة دور آخر لا تحمّل حزمة الجافاسكريبت الكسولة لذلك الدور وتعيد توجيه المستخدم تلقائياً. كما يتصفح الزوار الصفحات العامة فوراً دون تعليق على فحص الجلسة، ويُعاد توجيه المسجلين عند زيارة صفحات `/auth/**` إلى مساحة دورهم.

**سيناريوهات القبول**:

1. **معطى** زائر يدخل صفحة عامة، **عند** التوجيه، **يُسمح** له فوراً دون انتظار طلبات استعادة الجلسة.
2. **معطى** مستخدم مسجل بدور مختلف يحاول فتح مسار محمي بـ `roleGuard(role)` (`canMatch`)، **عند** مطابقة المسار، **يفشل** التطابق قبل تحميل أي Chunk كسول ويُحوّل إلى مسار دوره.
3. **معطى** مستخدم مسجل بدور مطابق، **عند** دخول مساحة دوره، **يُفتح** المسار بنجاح.
4. **معطى** مستخدم مسجل يزور `/auth/**` المحمية بـ `guestGuard`، **يُحوّل** تلقائياً عبر `UrlTree` إلى مسار دوره.
5. **معطى** إعادة تحميل مباشر لمسار دور محمي والـ status لا تزال `unknown`، **تستكمل** الاستعادة لمرة واحدة قبل الحسم بالقبول أو التحويل.

---

### قصة المستخدم 3 — القابلية للتمديد وفق مبدأ Open/Closed (الأولوية: P1)

يستطيع المطور إضافة استراتيجية دور سادس، أو عنصر تنقل لميزة مع تحديد الأدوار والترتيب، أو Interceptor جديد، أو بث/استقبال أحداث النطاق عبر `EventBusService` دون تعديل الكود القائم أو حقن منطق نقاط/ألعاب في `core/`.

**سيناريوهات القبول**:

1. تسجيل استراتيجية سادسة عبر `provideAuthStrategy(...)` دون تعديل الاستراتيجيات الخمس القائمة أو المصنع.
2. تسجيل عناصر تنقل عبر `provideNavItems(...)` وتصفيتها بالـ `role` وترتيبها حسب `order` عبر `NavService` دون لمس أي Shell.
3. بث واستقبال أحداث محددة النوع عبر `EventBusService` دون أي معالجات أعمال في المرحلة الثانية.
4. إضافة أي Interceptor مستقبلي في السلسلة المنظمة لـ `provideMozHttp()` دون إعادة كتابة الموجودين.

---

### قصة المستخدم 4 — توحيد اتصالات HTTP وتغذية راجعة مترجمة للأخطاء (الأولوية: P1)

كل طلب API خارجي يحمل `withCredentials: true` وترويسة اللغة النشطة `Accept-Language`. أخطاء الـ API تتحوّل إلى `AppError` موحد وتُعرض عبر Toast مترجم من مكتبة الواجهة (`shared/ui/toast`)، كما يلتقط `GlobalErrorHandler` الأخطاء غير المتوقعة، وتتعامل صفحة `NotFoundPageComponent` (`404`) مع الروابط المجهولة بنصوص مترجمة.

---

### قصة المستخدم 5 — إدارة SEO وحالة HTTP في بيئة SSR (الأولوية: P1)

عبر خدمة واحدة (`SeoService`) يمكن ضبط العنوان مع لاحقة المنصة، والوصف، و`canonical`، ووسوم Open Graph و Twitter، وروابط `hreflang` (`ar`/`en`/`x-default`)، وبيانات `JSON-LD` المنظمة (مع تنظيف الوسوم السابقة عند التنقل)، وتوجيه `noindex`، وإرجاع كود الحالة الحقيقي **`404`** في استجابة الـ SSR عبر `RESPONSE_INIT`.

---

### الحالات الحدّية (Edge Cases)

- **انتهاء الجلسة أثناء التصفح**: عند استلام `401` من أي طلب API غير طلب تسجيل الدخول، تستدعي السلسلة `AuthService.handleUnauthorized()` فتنظف الحالة وتنتقل لـ `anonymous` دون حلقات إعادة توجيه لانهائية.
- **عزل الطلبات المتزامنة في SSR**: انعدام أي متغيرات حالة عامة على مستوى الـ Module؛ كل طلب SSR يمتلك نسخة خدماته المعزولة.
- **عدم تعطيل الصفحات العامة**: لا ينتظر العرض العام في المتصفح أو SSR طلبات التحقق من الجلسة.
- **دور غير مسجل له استراتيجية**: رمي `AppError` من نوع `AUTH_STRATEGY_NOT_FOUND` بمفتاح مترجم.

## المتطلبات الوظيفية (`FR-001` إلى `FR-010`)

- **FR-001 (AC1)**: تجريد `AuthStrategy` + مصنع وسجل `AUTH_STRATEGIES` للأدوار الخمسة مع قابلية التمديد لدور سادس دون تعديل الكود القائم.
- **FR-002 (AC3)**: حالة الجلسة عبر الـ Signals (`user`, `role`, `status`, `isAuthenticated`) مع مزامنة `ThemeService`.
- **FR-003 (AC3)**: بقاء الجلسة عبر الخادم عند إعادة التحميل دون أي تخزين في `localStorage`/`sessionStorage` ودون حالة module-level.
- **FR-004 (AC2)**: توفير `roleGuard(role)` (`CanMatchFn`) و `roleRedirectGuard` و `guestGuard`.
- **FR-005 (AC4)**: سلسلة الـ Interceptors (`credentials`, `localeHeader`, `errorMapping`) + `AppError` + التنبيه عبر `ToastService` (`TOAST_PORT`).
- **FR-006 (AC5)**: `SeoService` + مولّدات `JSON-LD` + `noindex` + كود SSR `404` الحقيقي عبر `RESPONSE_INIT` + `public/robots.txt`.
- **FR-007 (AC6)**: سجل التنقل بـ multi-provider token (`NAV_ITEMS`, `provideNavItems()`, `NavService`).
- **FR-008 (AC7)**: ناقل أحداث نطاق محدّد النوع (`EventBusService`) خالٍ من منطق الألعاب/النقاط.
- **FR-009 (AC8)**: `GlobalErrorHandler` + صفحة `NotFoundPageComponent` + تغطية كافة النصوص بمفاتيح في `ar.json` و `en.json`.
- **FR-010 (AC9)**: اجتياز بوابات الجودة الأربع (`typecheck`, `lint` مع Sheriff و `i18n:check`, `test`, `build`) ومنع استيراد PrimeNG خارج `shared/ui` و `core/{theme,config}`.

## معايير النجاح القابلة للقياس (`SC-001` إلى `SC-008`)

- **SC-001**: نجاح استراتيجيات الأدوار الخمسة وإضافة استراتيجية سادسة في الاختبار دون لمس الاستراتيجيات القائمة.
- **SC-002**: تغطية كافة فروع الحراس (`anonymous`, `wrong role`, `right role`, `guestGuard`, `session restore`) مع إثبات عدم تحميل الشيفرة الكسولة عند الرفض.
- **SC-003**: `0` توكنات في `localStorage`/`sessionStorage` و`0` تسريب حالة عبر الـ injectors المنفصلة.
- **SC-004**: اختبارات الـ Interceptors تثبت إرسال الكوكيز وترويسة اللغة وتحويل الأخطاء وتشغيل التوست.
- **SC-005**: تحقق فعلي من مخرجات SSR لكود `404` ووسوم الـ SEO و`JSON-LD` و`noindex`.
- **SC-006**: اختبارات `NavService` تثبت التصفية والترتيب دون تعديل الـ Shell.
- **SC-007**: نجاح اختبارات `GlobalErrorHandler` و `EventBusService` و `NotFoundPageComponent` و`i18n:check`.
- **SC-008**: نجاح `typecheck` و `lint` و `test` و `build` بنسبة 100%.

## الافتراضات وخارج النطاق

- الـ APIs محاكية حالياً خلف `AuthApi` (`MockAuthApi`) لحين تأكيد عقد الباك إند النهائي (`HttpAuthApi`).
- خارج النطاق في هذه المرحلة: الاتصال الفعلي بالباك إند، شاشات تسجيل الدخول الحقيقية، قوالب الإطارات البصرية (Shells)، المحفظة والعملات، الميزات الاجتماعية، وSEO الصفحات التجارية المحددة (تُبنى في المرحلة الثالثة).
